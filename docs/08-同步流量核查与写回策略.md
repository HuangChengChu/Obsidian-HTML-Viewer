# 08 · 同步流量核查与写回策略

> 核查日期：2026-11-05
> 核查对象：本机 Obsidian 插件 `nutstore-sync`（坚果云 WebDAV 同步）+ 本插件 `html-single-file-view`
> 核查方式：读两个插件的源码 + 在真机上逐阶段实测写盘次数（`scripts/probe-write-amplification.mjs`）
> 结论一句话：**你的担心成立——标注确实是「一次标注 = 一次整文件上传」；但「打开/关闭文件」并不会传数据。**

---

## 1. 结论速览

| 问题 | 结论 |
| --- | --- |
| 坚果云同步是增量还是整文件覆盖？ | **整文件覆盖**。WebDAV `PUT`，每次上传整个文件，没有分块、没有差分、没有压缩 |
| 插件会不会「打开文件就传一次」？ | **不会**。实测打开和关闭都是 **0 次写盘** |
| 一次标注传多少？ | **1 次整文件上传**。3.5 MB 的文件 = 3.5 MB 上行 |
| 连续操作会不会叠加？ | **不会**。500 ms 内的连续改动被防抖合并成 1 次（实测连打 5 次 = 1 次） |
| 免费版额度够不够？ | 坚果云免费版 **上传 1 GB/月、下载 3 GB/月**。10 个大文件各标 15 次 = 约 525 MB，一次吃掉一半额度 |
| 有效信息占比 | 标注数据只有几 KB，文件 3.5 MB → **真正变化的内容占 0.1%**，其余全是重复上传 |
| 能不能在插件里把上传变小？ | **不能**。WebDAV `PUT` 是全有或全无，能动的只有「写盘次数」和「换同步方式」 |

## 2. 机制核查（读源码）

### 2.1 上传路径：整文件 PUT

坚果云同步插件内置了一个 WebDAV 客户端，它**具备**局部更新能力：

```js
partialUpdateFileContents: function (h, v, y, m, b) { return d$e(x, h, v, y, m, b); }
```

但在整份 `main.js`（982 KB）里，`partialUpdateFileContents` **只出现 1 次，就是上面这行方法定义本身**——同步逻辑从来没有调用过它。

真正被调用的是：

```js
this.webdav.putFileContents(this.remotePath, <整个文件的字节>, { overwrite: true })
```

三处上传点（单文件、二进制、文本冲突合并）全都是这一句。**每次上传 = 整个文件过线。**

### 2.2 没有任何压缩

全文件里搜不到 `Content-Encoding`，也搜不到 `contentEncoding`，上传的是原始字节。
（代码里确实有一处 gzip，但那是给「远端元数据缓存目录」用的，不是文件内容。）

### 2.3 只传「变化过的文件」——这是唯一的缓解

同步时按 `mtime` + `size` 比对本地和远端，只有变了的文件才会进上传队列。
所以**不是**每次同步都重传整个 vault。

### 2.4 触发时机

| 事件 | 行为 |
| --- | --- |
| `vault.on("modify")` | `realtimeSync: true` → **立刻**提交一次同步 |
| 定时 | `autoSyncIntervalSeconds: 600` → 每 10 分钟全量比对一次 |
| 冲突 | `conflictStrategy: "diff-match-patch"` → **需要把两侧文件都下载下来**做三方合并（流量翻倍） |

### 2.5 两个被误解的概念（排除）

- **`useGitStyle`**：只是「冲突时用 `<<<<<<<` 标记而不是 HTML 标签显示」，**与传输方式无关**。你当前是 `false`。
- **`diff-match-patch`**：只在**真的产生冲突**时用来合并内容，不是增量同步算法。日常不会触发。

### 2.6 你的实际配置（读自 vault 的 `data.json`）

```json
{
  "realtimeSync": true,
  "autoSyncIntervalSeconds": 600,
  "conflictStrategy": "diff-match-patch",
  "syncMode": "loose",
  "skipLargeFiles": { "maxSize": "30 MB" },
  "useGitStyle": false
}
```

## 3. 真机实测：每个动作触发几次写盘

脚本：`scripts/probe-write-amplification.mjs`（用插件调试日志里「写回成功」条数逐阶段计数）

```
样例文件 109524 字节（107.0 KB）

【打开】写盘 0 次；文件是否被改写=false；mtime 变化=false
【作答 1 次】写盘 1 次；文件已改写=true
【再连打 5 次作答】写盘 1 次（500ms 防抖合并后应该 ≈1，而不是 5）
【滚动阅读 630px，只看不改】写盘 1 次（章节进度变化会触发保存）
【关闭标签页】写盘 0 次

合计写盘 3 次
```

### 3.1 逐项解读

| 动作 | 写盘 | 为什么 |
| --- | --- | --- |
| **打开文件** | **0** | 页面收到磁盘上的进度后**不会**回写。`applyProgress()` 里没有 `saveNow()`；唯一那处 `saveNow()` 在 `mergeLocal()` 里，只有「降级模式攒了本地数据」才会走到 |
| **作答 / 标注 / 笔记** | **1** | `change` 事件 → `scheduleSave()` → 500 ms 后 `saveNow()` → 插件合并写盘 |
| **500 ms 内的连续操作** | **1** | 防抖合并（`SAVE_DEBOUNCE = 500`）。连打 5 次只写 1 次 |
| **滚动跨章节** | **1** | `updateSectionProgress()` 发现章节已读状态变了 → `scheduleSave()`。不跨章节就不写 |
| **关闭文件** | **0** | `beforeunload` 里确实有 `saveNow()`，但此时插件视图已先被销毁，消息发不出去，实测没有额外写盘 |

### 3.2 修正后的流量账（按你的真实文件 3.5 MB）

| 场景 | 上传次数 | 上行字节 |
| --- | --- | --- |
| 打开看一眼就关 | 0 | **0** |
| 连续 5 次作答（手速快） | 1 | 3.5 MB |
| 读完整篇（滚动跨章节） | 1 | 3.5 MB |
| **标注 15 次（每条之间有思考停顿）** | **15** | **52.5 MB** |

**关键点：防抖只覆盖 500 ms 内的连续操作。** 真人标注是「选中 → 打字 → 确认 → 再选下一段」，
每条之间隔好几秒，所以**每条标注 = 1 次完整上传**。这正是你担心的那个场景，确实成立。

10 个文件各标 15 次 → **约 525 MB**，一次性吃掉免费版月上传额度的一半。

## 4. 改进方案

### 方案 A · 写回策略可选（**插件内可做，收益最大**）

插件设置里加一项「写回时机」：

| 选项 | 行为 | 省多少 | 代价 |
| --- | --- | --- | --- |
| **即时**（现状，默认） | 改动后 500 ms 写盘 | — | 每次标注 = 3.5 MB |
| **合并延迟 N 秒** | 改动后 N 秒内不再写，N 秒到或页面失焦时才写 | 15 条标注从 15 次降到「停顿次数」次 | 手机上要等 N 秒才看到 |
| **手动** | 只在点「保存」时写盘 | 降到 0 | 跨设备接力不再是实时的 |

**推荐默认值：`合并延迟 5 秒`。** 5 秒内的连续操作合并成 1 次，
真人「选一段→写评注→确认→立刻选下一段」的节奏基本能合并掉一部分，
而「合上电脑立刻在手机上看」最多晚 5 秒，完全可接受。

再加一条兜底：**页面失焦 / 标签页关闭时立刻冲刷**（现在是 0 次写盘，改成冲刷一次）。
这样「延迟」不会丢数据。

### 方案 B · 内容没变就不写盘（**实测收益很小，可不做**）

比对「有意义内容」（`answers` / `notes` / `annotations` / `marks` / `strokes` /
`sectionProgress` / `ui`，**不含 `meta.updatedAt`**）与磁盘数据块，一致就不写。

实测下来：打开 0 次、关闭 0 次、滚动只在跨章节时写 1 次——**几乎不存在「触发了保存但内容没变」的情况**。
所以这条基本是空转，只在极端情况下省一次。**建议放到方案 A 之后再看要不要做。**

### 方案 C · 把大文件排除出坚果云同步（**你决定**）

把 `nutstore-sync` 的 `skipLargeFiles.maxSize` 从 `30 MB` 调到 `3 MB`：

- 大 HTML 直接**跳过不同步** → 0 流量
- 代价：**大文件失去跨设备接力**，而这正是本插件的核心价值
- 只适合「我只想同步笔记，大文件我自己在电脑上用」

### 方案 D · 进度单独存一个文件（**能根治，但和你定的约束冲突**）

把进度数据从 HTML 文件里搬出来，单独存一个小文件（比如 `.hvv/xxx.json`，几 KB）：

- 只改进度 → 只传几 KB → **流量降低约 700 倍**
- 彻底解决「几兆 × 十几次」的问题
- **代价：违背你定的「零附属文件」硬约束**，而且 HTML 单文件发给别人时进度不跟着走

**我把它摆出来，是因为这是唯一能根治的方案**，但要不要改由你定。

### 方案 E · 换同步方式（风险高，不推荐现在动）

坚果云**桌面客户端的「同步文件夹」模式**用的是块级差分协议，官方明确说
「只上传不同版本间的差异内容」。理论上 3.5 MB 文件末尾改 5 KB → 只传几 KB。

但 Obsidian 运行中用桌面客户端同步同一份 vault 会产生文件级冲突，得不偿失。

### 已经做对的一件事

本插件把数据区放在文件**最末尾**（`</body>` 前）。对 WebDAV 无用，但如果将来换成
支持块级差分的同步方式，这是**最优布局**——改动只落在文件尾部那几个字节。
不需要为此做任何调整。

## 5. 推荐组合

**方案 A（写回策略，默认「合并延迟 5 秒」+ 失焦/关闭冲刷）** 落地，
其余保持现状。理由：

- 只改插件内部，不动同步插件、不动你的文件结构、不违背任何硬约束
- 对「标注十几次」这个具体场景，预计能省掉 30–60% 的上传
- 方案 D 虽然能根治，但要先解除「零附属文件」这条约束——这是你的决策，不是我的
